Organization Foundation File Guide
==================================

Purpose of this file
--------------------
This file explains the organization foundation added after auth. It focuses on the revised product rule that users cannot create organizations directly. Users can only submit organization access requests, and only a super admin can create an organization after review.

Migrations and why they exist
-----------------------------

1. database/migrations/2026_03_15_000001_add_platform_role_to_users_table.php
- Adds `platform_role` to users.
- Needed to distinguish normal users from `super_admin`.
- This is platform-level access, not organization membership role.

2. database/migrations/2026_03_15_000002_create_organizations_table.php
- Creates the `organizations` table.
- Stores the organization record that will later own social accounts, posts, schedules, logs, and settings.
- Includes `created_by` so super-admin-created organizations stay auditable.

3. database/migrations/2026_03_15_000003_create_organization_members_table.php
- Creates the membership table between users and organizations.
- Stores per-organization role data such as `organization_admin` and `user`.
- Keeps org access scoped through memberships instead of through user table columns.

4. database/migrations/2026_03_15_000004_create_organization_access_requests_table.php
- Stores user requests to become an organization customer.
- Tracks requested organization name, contact details, message, approval status, reviewer, review notes, and linked organization.
- This table is the audit trail for the “contact us to become an organization” flow.

Main files and responsibilities
-------------------------------

1. app/Models/Organization.php
- Represents an approved organization.

2. app/Models/OrganizationMember.php
- Represents a user membership inside an organization.

3. app/Models/OrganizationAccessRequest.php
- Represents the request submitted by a user asking for organization access.

4. app/Models/User.php
- Now includes `platform_role`, org memberships, and org access request relationships.

5. app/Providers/AuthServiceProvider.php
- Defines the `access-super-admin` gate for admin-only organization creation.

6. app/Http/Requests/Organization/StoreOrganizationAccessRequest.php
- Validates the user-side “become an organization” request.

7. app/Http/Requests/Admin/CreateOrganizationFromRequest.php
- Validates the super-admin organization provisioning request.

8. app/Services/Organization/OrganizationAccessRequestService.php
- Handles user submission and listing of access requests.

9. app/Services/Organization/OrganizationProvisioningService.php
- Handles organization creation from an approved request, initial membership, and notification dispatch.

10. app/Http/Controllers/Organization/StoreOrganizationAccessRequestController.php
- User endpoint for submitting an organization access request.

11. app/Http/Controllers/Organization/MyOrganizationAccessRequestsController.php
- User endpoint for listing only the current user’s own organization requests.

12. app/Http/Controllers/Admin/ListOrganizationAccessRequestsController.php
- Super-admin endpoint for reviewing all access requests.

13. app/Http/Controllers/Admin/CreateOrganizationController.php
- Super-admin endpoint for approving a request and creating the organization.

14. app/Http/Resources/OrganizationResource.php
- Shapes organization payloads returned to the frontend.

15. app/Http/Resources/OrganizationAccessRequestResource.php
- Shapes organization access request payloads returned to the frontend.

16. app/Notifications/OrganizationApprovedNotification.php
- Emails the requester when their organization access has been approved and provisioned.

17. app/Services/Auth/AuthResponseService.php
- Now includes current organization context and organization request status in the auth payload.

18. tests/Feature/Organization/OrganizationAccessRequestTest.php
- Covers user-side request submission and request listing.

19. tests/Feature/Admin/OrganizationProvisioningTest.php
- Covers super-admin provisioning, admin-only access, and updated auth context.

Where future related changes should go
--------------------------------------
- Rejection flow: keep it on `organization_access_requests` with admin service/controller updates.
- Support notes or review states: extend the request table and provisioning/review services.
- Multi-organization switching: expand auth response and membership handling, not the users table.
- Frontend dashboard status views: consume `organization_access_requests` and `auth/me` organization context.

==================================
2026-03-19 Frontend Contract Update
==================================

The active frontend organization screen now uses a request-based onboarding contract with these endpoints:

- `POST /api/organization-requests`
- `GET /api/organization-requests/latest`
- `DELETE /api/organization-requests/{id}`
- `GET /api/organizations/current`
- `GET /api/admin/organization-requests`
- `POST /api/admin/organization-requests/{id}/approve`
- `POST /api/admin/organization-requests/{id}/reject`
- `GET /api/admin/organizations`

To support that contract, the organization tables were expanded with a new migration:

- `database/migrations/2026_03_19_130000_expand_organization_tables_for_frontend_flow.php`

This migration adds the fields that the live frontend organization request form actually submits and displays:

- On `organization_access_requests`
  - `contact_person_name`
  - `timezone`
  - `bio`
  - `location`
  - `industry`
  - `organization_size`

- On `organizations`
  - `timezone`
  - `contact_person_name`
  - `contact_person_email`
  - `contact_person_phone`
  - `website`
  - `bio`
  - `location`
  - `industry`
  - `organization_size`

Important implementation notes:
- The backend still uses the existing normalized tables instead of creating a second organization flow.
- `OrganizationAccessRequestResource` was reshaped to the camelCase payload expected by the current Next.js frontend.
- Approval now creates an `organizations` row and an `organization_members` owner row so the requester becomes the organization owner after super-admin approval.
- Withdraw only allows the requesting user to remove their own pending or rejected request.

Current testing coverage now includes:
- user request submission
- duplicate pending-request protection
- latest-request retrieval
- user request withdrawal
- super-admin approval
- super-admin rejection
- admin access restrictions

2026-03-19 Members and Invites
==================================

New backend files for this chunk:

- `database/migrations/2026_03_19_140000_create_organization_invites_table.php`
- `app/Models/OrganizationInvite.php`
- `app/Http/Resources/OrganizationMemberResource.php`
- `app/Http/Resources/OrganizationInviteResource.php`
- `app/Http/Requests/Organization/StoreOrganizationInviteRequest.php`
- `app/Http/Requests/Organization/UpdateOrganizationMemberRequest.php`
- `app/Http/Requests/Organization/AcceptOrganizationInviteRequest.php`
- `app/Services/Organization/OrganizationMemberService.php`
- `app/Http/Controllers/Organization/ListOrganizationTeamController.php`
- `app/Http/Controllers/Organization/StoreOrganizationInviteController.php`
- `app/Http/Controllers/Organization/UpdateOrganizationMemberController.php`
- `app/Http/Controllers/Organization/RemoveOrganizationMemberController.php`
- `app/Http/Controllers/Organization/RevokeOrganizationInviteController.php`
- `app/Http/Controllers/Organization/PreviewOrganizationInviteController.php`
- `app/Http/Controllers/Organization/AcceptOrganizationInviteController.php`

What these files do:

- `organization_invites` stores pending organization membership invitations with token-based acceptance.
- `OrganizationMemberService` is the main business layer for team listing, invite creation, role changes, removals, revocation, preview, and acceptance.
- `OrganizationMemberResource` gives the frontend a stable row shape for active team members.
- `OrganizationInviteResource` gives the frontend a stable row shape for pending invites, including a shareable invite URL.
- `StoreOrganizationInviteRequest` validates the invite email and restricts allowed invite roles to `manager` and `editor`.
- `UpdateOrganizationMemberRequest` validates allowed role changes and intentionally excludes owner transfer.
- `AcceptOrganizationInviteRequest` validates name and password for invite acceptance.

Live endpoints added:

- `GET /api/organizations/current/team`
- `POST /api/organizations/current/invites`
- `PATCH /api/organizations/current/members/{id}`
- `DELETE /api/organizations/current/members/{id}`
- `DELETE /api/organizations/current/invites/{id}`
- `GET /api/invites/{token}`
- `POST /api/invites/{token}/accept`

Important implementation notes:

- Active members and pending invites are now separate concepts in the data model. Pending people remain in `organization_invites` until they accept.
- Only organization owners can manage team composition in this chunk.
- Invite acceptance returns the same auth payload shape used by login so the frontend can establish a session immediately.

Current testing coverage added for this chunk:
- current team listing
- owner invite creation
- non-owner invite rejection
- member role update
- member removal
- invite preview
- invite acceptance by a new user
