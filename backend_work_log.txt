Chunk 2 - Auth Foundation With Sanctum SPA Cookies
========================================

1. What was added
- Added the day-one authentication API for register, login, logout, me, forgot password, and reset password under the `/api/auth` route group.
- Added dedicated Form Request classes for each auth endpoint so validation stays out of controllers and the request contract remains stable for the Next.js frontend.
- Added auth service classes to handle registration, login, password reset link dispatch, password reset completion, and authenticated user payload formatting.
- Added `AuthUserResource` and a shared auth response payload that includes a first-pass onboarding state for future organization setup.
- Added a reusable API response trait and exception handler JSON formatting so success, validation failure, and unauthorized responses follow one predictable structure.
- Enabled Sanctum stateful SPA middleware and updated CORS/session-related configuration to support credentialed requests from the frontend.
- Added feature tests for the auth flow and created this backend work log file for ongoing chunk-by-chunk tracking.

2. What each part does
- The auth controllers now act only as orchestration points. They receive validated input, call the appropriate service, and return the standardized JSON response shape expected by the frontend.
- The Form Requests define endpoint-level validation rules for registration, login, forgot password, and reset password so invalid input fails consistently before reaching business logic.
- `RegisterService` creates the user inside a database transaction, signs the user into the web guard, regenerates the session, and returns the authenticated payload.
- `LoginService` checks credentials through Laravel authentication, regenerates the session on success, and returns the same authenticated payload shape used by registration and the me endpoint.
- `ForgotPasswordService` uses Laravel’s password broker to trigger the reset notification flow without exposing whether an email exists in the system.
- `ResetPasswordService` completes password changes through the password broker, updates the remember token, and fires Laravel’s password reset event.
- `AuthResponseService` centralizes the authenticated response body so register, login, and me all return the same frontend-friendly structure.
- `AuthUserResource` exposes stable user fields only, which reduces the chance of accidental data leakage as the user model grows later.
- The exception handler now formats validation and unauthenticated errors into the agreed API contract, removing inconsistency across auth endpoints.
- `AppServiceProvider` now rewrites password reset URLs to the frontend reset page so the user completes the reset inside the Next.js app instead of the backend.
- The CORS and Sanctum changes allow credentialed SPA requests and prepare the backend for same-site or subdomain-based deployment.

3. Important implementation decisions
- Sanctum was configured in SPA cookie mode because the current plan expects a Next.js dashboard using session-based authentication rather than long-lived API tokens for first-party frontend requests.
- A shared API response trait was introduced to keep endpoint responses predictable without pushing response formatting into every controller method manually.
- Auth payload building was extracted into a dedicated service so onboarding metadata can be expanded later without rewriting each auth endpoint separately.
- The onboarding response currently returns `organization_required: true` and `organization_id: null` so the frontend can route new users into the later workspace onboarding flow without coupling this chunk to organization creation.
- Password reset URLs are built from `FRONTEND_URL` so the reset flow stays aligned with frontend routing and remains configurable between local and production environments.
- CORS was changed from wildcard origins to explicit frontend URLs because Sanctum SPA cookie authentication requires credentialed requests and should not run with unrestricted cross-origin settings.
- Validation and unauthorized JSON formatting were placed in the exception handler so future API modules can inherit the same error contract automatically.

4. Notes for frontend integration
- The frontend should call `/sanctum/csrf-cookie` before posting to login or register when using Sanctum SPA cookie authentication.
- Auth endpoints available now are `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `POST /api/auth/forgot-password`, and `POST /api/auth/reset-password`.
- Successful authenticated responses return `data.user` and `data.onboarding`, where `onboarding.organization_required` is currently always `true`.
- Validation failures return `success: false`, the message `The given data was invalid.`, and an `errors` object keyed by field name.
- Unauthorized requests return `success: false` and the message `Unauthorized.` with HTTP 401.
- The frontend reset-password page should accept `token` and `email` query parameters because the backend now generates reset links in that format.
- For production cookie auth, frontend and backend domain settings must match the deployed domain strategy, especially `SANCTUM_STATEFUL_DOMAINS`, `SESSION_DOMAIN`, and secure cookie behavior.

5. Pending or next steps
- Add organization/workspace creation and membership flow in the next chunk so onboarding can move from a placeholder flag to real tenant context.
- Add organization-aware auth context after the organization tables exist so the me endpoint can include active organization information safely.
- Review production session and cookie settings once the final frontend and backend domains are confirmed, because fully cross-site cookie auth will require stricter cookie configuration than local development.
- Add email verification only if that requirement is introduced later, since this chunk intentionally keeps the MVP auth foundation focused on account access and password recovery.

2. What each part does

- `ProfileService` now contains the account deletion logic, including current-password verification and avatar file cleanup.
- The frontend settings popup now shows a real danger zone with current-password entry and a delete action button.

3. Important implementation decisions
- Logout happens before deletion because Laravel's logout flow can touch remember-token state on the in-memory user model; doing it afterward can accidentally recreate the deleted row.
- Account deletion requires the current password so destructive self-delete is not triggered by an open session alone.
- Existing user-linked organization membership and access-request rows remain safe because those tables already use user foreign keys that cascade on delete.

4. Notes for frontend integration
- Active delete-account endpoint is:
- `DELETE /api/profile`
- Request body:
- `{"current_password":"..."}`
- The frontend now asks for the current password in the danger zone and shows a confirmation dialog before deletion.
